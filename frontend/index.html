Q1 : Explain the difference between SAML and OAuth. When would a company choose one over the other?

SAML and OAuth differ at the core: SAML is about proving who the user is, while OAuth is about controlling what an application is allowed to do. SAML provides authentication and enterprise single sign-on, typically using XML assertions passed between an identity provider and a service provider. OAuth, by contrast, provides delegated authorization — it lets a user grant a third-party app limited access to their data without sharing credentials.

In practice, companies choose between them based on the problem they're solving. When the goal is workforce login — employees accessing SaaS tools like Salesforce, Slack, or internal portals — SAML fits because it cleanly federates identity across systems and gives a seamless SSO experience. It answers the question “Who is this user?” and is widely adopted in enterprise environments.

OAuth becomes the right choice when the company needs controlled access to APIs or wants apps to act on a user's behalf. It's used when a service needs permission to read a calendar, post to a repository, or access cloud storage without ever seeing the user's password. It answers “What is this app allowed to do?” and is the backbone of modern API security.

A modern architecture often uses both: SAML for employee login, OAuth (usually with OpenID Connect added) for mobile apps, SPAs, and third-party integrations. The decision isn't about which protocol is better overall — it's about choosing the one that matches the layer of identity you're dealing with.

Q2 : What are open data portals(for example avoindata.fi or the European Data Portal) and why does choosing the right open-data format matter for reuse?

Open data portals such as avoindata.fi and the European Data Portal are public platforms that collect, catalogue, and publish machine-readable datasets produced by governments, public agencies, cities, and other organisations. They exist to make public-sector information easy to find, access, and reuse. Finland's avoindata.fi, for example, provides access to more than 2,300 datasets and offers APIs, search tools, and guidelines that help organisations publish data in a standardised way, while also ensuring the data is harvested into the wider European ecosystem. The European Data Portal plays a similar role at the EU level, offering tools for bulk download, metadata quality assessment, interoperability guidance, and training resources to help people use and publish open data effectively.

Choosing the right open-data format matters because it directly affects how easily others can reuse the data. Open data is defined as digital, machine-readable information with an open licence, meaning anyone can use it for any purpose. But “machine-readable” is not just a label — it determines whether developers, researchers, and companies can actually work with the data. A well-chosen format (such as CSV, JSON, GeoJSON, or XML) allows software tools to process the data automatically, combine it with other datasets, and build applications or visualisations without manual cleaning. Poor formats — PDFs, images, inconsistent spreadsheets — make reuse difficult or impossible because they require heavy preprocessing and often lose structure or precision.

Portals like avoindata.fi emphasise standardisation because consistent formats improve interoperability across organisations and countries, enabling cross-border collaboration and innovation. The European Data Portal reinforces this by providing guidelines and tools for metadata quality and standardised publishing, ensuring datasets can be integrated into larger systems and reused at scale.

Q3 : What is YAML and why has it become the default configuration format for Kubernetes/Rahti manifests? Compare it briefly to JSON.

YAML is a human-friendly data-serialization format designed to be easy to read and write. Its name literally means “YAML Ain't Markup Language”, which hints at its purpose: it isn't meant to describe documents like HTML or XML, but to express structured data in a way that feels natural to humans. YAML uses indentation instead of braces, supports comments, and avoids unnecessary punctuation, which makes configuration files feel more like clean, readable text rather than code.

Kubernetes (and Rahti, which is built on OpenShift/Kubernetes) adopted YAML as the default format for manifests because readability matters enormously when you're defining complex infrastructure. A Kubernetes manifest often contains nested objects, lists, metadata, and specifications for pods, deployments, services, volumes, secrets, and more. YAML's indentation-based structure makes these relationships visually clear, helping developers and operators understand the hierarchy at a glance. YAML also supports anchors, aliases, and multi-line strings, which are useful for large configurations. Most importantly, YAML is flexible enough to represent Kubernetes' declarative model: you describe the desired state, and the system reconciles it.

JSON can represent the same data, and Kubernetes actually accepts JSON for all manifests. But JSON is more rigid and verbose. It requires braces, brackets, and quotes everywhere, and it doesn't allow comments. A Kubernetes Deployment written in JSON is significantly harder to scan visually, especially when nested several levels deep. YAML's cleaner syntax reduces cognitive load and makes configuration errors easier to spot. In practice, YAML became the default because it's simply more comfortable for humans, even though Kubernetes internally converts YAML to JSON before processing it.

Q4 : Explain what a peer-to-peer VPN(for example n2n) is used for, and how it differs from a traditional site-to-site VPN?

A peer-to-peer VPN such as n2n creates a direct encrypted tunnel between individual devices, letting them communicate as if they were on the same local network even when they're physically far apart. Instead of routing traffic through a central gateway, each device becomes a peer in a virtual LAN. n2n uses a lightweight “supernode” only to help peers discover each other; once connected, the traffic flows directly between endpoints. This makes peer-to-peer VPNs useful for small teams, IoT deployments, ad-hoc remote access, home-lab setups, or situations where devices need to talk directly without a full corporate network behind them.

A traditional site-to-site VPN, by contrast, links entire networks together. Each site has a gateway (usually a firewall or router) that maintains a persistent tunnel to the other site. All devices behind each gateway can reach the remote network without running VPN software themselves. This model is used for branch offices, data centers, cloud VPCs, and enterprise WANs, where the goal is to merge two networks into one continuous private environment.

The difference is architectural: peer-to-peer VPNs connect hosts to hosts, while site-to-site VPNs connect network to network. Peer-to-peer tunnels are typically lightweight, flexible, and on-demand; site-to-site tunnels are persistent, infrastructure-level, and designed for large-scale routing between subnets. The choice depends on whether you need direct device-to-device communication or full network integration.

Updated Application Overview and Application Architecture

The architecture from Assignment 4 was extended by adding a Redis cache to the application. The original frontend, backend, and MySQL database remain in place, while Redis is now used by the backend to store the page-view counter.

Redis is therefore not part of the backend pod. It operates independently alongside the existing Week 4 pods and communicates with the backend through the OpenShift internal network. This demonstrates how an additional containerized caching service can be integrated into the existing application without modifying the original frontend, backend, and database structure.

Experiments

1. Delete the Redis Cache Pod

The Redis cache pod was deleted from the OpenShift project to observe how the application behaves when the cache pod is removed.

After deleting the cache pod, OpenShift automatically recreated the pod because the Redis deployment was configured to maintain the desired number of replicas.

I also checked the visit count before and after deleting the Redis pod. After the Redis pod was recreated, the visit count started again from 1. This happened because the page_views counter was stored in Redis, and the new Redis pod did not retain the previous counter value.

This experiment demonstrated that the visit counter stored in Redis is temporary and can be lost when the Redis pod is recreated if persistent storage is not configured for Redis.

This demonstrated the difference between the Redis cache and the MySQL database. The database data was preserved because it was stored in persistent storage, while the Redis counter was reset when the Redis pod was recreated.

Most Important Problem Encountered and How I Solved It

The most important problem encountered during the Redis integration was a 500 Internal Server Error when accessing the /api/visits endpoint. The backend logs showed that Redis had disabled write operations because it was unable to save its RDB snapshot to the /data directory. The Redis logs reported a permission error when trying to create the temporary RDB file.

To solve the problem, I updated the Redis Deployment YAML to disable RDB snapshot saving: command: ["redis-server"] args: ["--save", ""]

With RDB snapshot saving disabled, Redis no longer attempts to create the RDB files that were causing the permission error. After redeploying the Redis pod with this configuration, the backend was able to increment the Redis counter successfully. I verified the solution through the /api/visits endpoint, where the visit counter increased with each request. This confirmed that the backend was successfully communicating with the standalone Redis pod and that Redis was correctly handling the in-memory counter.
